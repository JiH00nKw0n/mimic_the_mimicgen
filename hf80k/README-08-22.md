# FR3 합성 데이터 생성 파이프라인 (2026-08-22 기준)

사람이 로봇을 조종해 녹화한 시연 몇 편을 넣으면, 배치와 조명과 물리가 서로 다른 성공
에피소드를 원하는 만큼 만들어 LeRobot 데이터셋 형식으로 허깅페이스에 올리는 파이프라인이다.
컨테이너 하나가 다섯 단계를 끝까지 수행한다.

이 문서 하나로 두 가지를 알 수 있다. 무엇을 어디에 놓고 어떤 명령을 치면 무엇이 나오는지,
그리고 지금 무엇이 되고 무엇이 안 되는지다.

## 2. 무엇이 들어가서 무엇이 나오는가

```
입력   표시된 시연 HDF5 | 실측 물리 번들 | 시각 규격 패키지 | .env

  0. 소스 고르기   source_filtered.hdf5   수율 0인 시연을 뺀 사본
  1. 생성          gen.hdf5               새 배치에서 성공한 궤적만
  2. 변환          contract.hdf5          실기가 받는 명령 형식
  3. 렌더          rgb.hdf5               카메라 3대 영상
  4. 기록          lerobot/               LeRobot v3 데이터셋
  5. 업로드                               허깅페이스 저장소로

출력   허깅페이스 저장소의 LeRobot v3 데이터셋
```

단계마다 무엇이 들어가고 나오는지는 `PIPELINE.md`에 배열 모양까지 적혀 있다. 청크(기본
500편) 단위로 0단계부터 5단계까지 돌고, 청크가 끝날 때마다 바로 올라가고 중간 파일은
지워진다. 중간에 멈춰도 끝난 청크는 건너뛴다.

한 프레임에 들어가는 것은 카메라 3종 영상(3×180×320), 상태 23개(관절 각도 9, 손끝 자세 7,
직전 명령 7), 행동 7개, 시각 프로파일 번호다. 초당 10프레임이다.

## 4. 어떤 명령을 치는가

전부 `hf80k` 폴더 안에서 실행한다.

```bash
cp .env.example .env      # 허깅페이스 토큰과 저장소 이름을 채운다
make check                # 자산과 .env가 갖춰졌는지 본다
make build                # 이미지를 굽는다. 처음에는 30분에서 40분
make smoke                # 100편으로 동작을 확인한다
make run                  # 본 실행. .env의 TARGET_EPISODES 만큼
make aggregate WORK=...   # 끝나면 합쳐서 최상위에 올린다
```

GPU가 네 장이면 `make run` 대신 `make run-4gpu`를 쓰고, 합칠 때 작업 디렉터리를 전부
넘긴다(`make aggregate WORK='/data/hf80k/gpu*'`). 하나만 넘기면 그 한 대분만 담긴
데이터셋이 오류 없이 만들어진다.

핀 삽입으로 돌리려면 `.env`에 한 줄을 더한다.

```
TASK_PROFILE=peg_insert_fr3
```

표시가 없는 원본 시연에서 시작한다면 그 앞에 한 단계가 더 있다.

```bash
make annotate INPUT=/path/raw.hdf5 OUTPUT=/abs/path/annotated.hdf5
```

## 5. 태스크를 바꾸는 방법

태스크마다 다른 값이 `src/profiles/<이름>.yaml` 한 장에 모여 있다. `.env`의
`TASK_PROFILE`로 고른다. 파이프라인 다섯 단계는 그대로 두고 태스크만 바뀐다.

프로필 한 장이 정하는 값을 전부 적으면 아래와 같다. 같은 뜻의 환경변수를 밖에서 주면
그쪽이 이긴다.

| 프로필 키 | 무엇을 정하는가 | 큐브 쌓기 | 핀 삽입 |
|---|---|---|---|
| `generate.task_id` | Isaac에 등록된 생성 환경의 이름이다. | `Isaac-Stack-Cube-LabFR3-HF80K-Fwd-IK-Rel-Mimic-v0` | `Isaac-PegInsert-LabFR3-IK-Rel-Mimic-v0` |
| `generate.register_modules` | 생성 스크립트 앞에 끼워 넣을 모듈이다. 환경 등록과 성공 판정 훅이 여기 들어간다. | `lab_register`, `clean_success_hook`, `provenance_hooks` | `peg_register`, `peg_success_hook`, `provenance_hooks` |
| `generate.module_dir` | 위 모듈이 들어 있는 폴더 이름이다. `src/` 아래에서 찾는다. | `env` | `env_peg` |
| `generate.source_hdf5` | 구간 경계 표시가 붙은 사람 시연 파일이다. `assets/` 아래에서 찾는다. | `fwd_annotated.hdf5` | `peg_annotated.hdf5` |
| `generate.source_yield_json` | 소스 시연별 성공률 측정치다. 수율 0인 시연을 빼는 데 쓴다. 빈 값이면 전부 쓴다. | `source_yield.json` | 빈 값 |
| `generate.arm_scale` | 한 스텝에 허용하는 손끝 이동량의 배율이다. 작으면 멀리 있는 물체까지 도달하지 못한다. | 0.5 | 1.0 |
| `generate.subtask_offsets` | 구간 경계를 원래 자리보다 몇 스텝 뒤로 옮길지 정하는 "최소,최대"다. 매번 그 범위에서 하나를 무작위로 뽑는다. | 10,20 | 10,20 |
| `generate.action_noise` | 매 스텝 명령에 더하는 잡음의 크기다. 0이면 넣지 않는다. | 적지 않음(환경 코드 기본값 0.03) | 0.0 |
| `generate.num_interpolation_steps` | 구간이 바뀔 때 손을 다음 구간의 시작 자세까지 몇 스텝에 걸쳐 옮길지다. | 적지 않음(환경 코드 기본값 5) | 적지 않음 |
| `generate.extra_env` | 생성·변환·렌더에 그대로 넘길 환경변수다. | 없음 | 핀과 구멍 3D 모델 경로 두 개 |
| `convert.object_states` | 계약 형식에 자세를 기록할 강체 이름이다. 시연 파일의 `states/rigid_object/<이름>/root_pose`에서 읽는다. | `cube_1`, `cube_2`, `cube_3` | `peg` |
| `render.task_id` | 렌더가 궤적을 다시 재생할 환경의 이름이다. | 빈 값(기본 큐브 장면) | `Isaac-PegInsert-LabFR3-IK-Rel-Mimic-v0` |
| `render.register_modules` | 렌더 스크립트 앞에 끼워 넣을 모듈이다. | 없음 | `peg_register` |
| `render.cameras` | 영상으로 남길 카메라다. | 3인칭 두 대와 손목 한 대 | 같음 |
| `render.overlay_yaml`, `render.binding_yaml` | 실측한 카메라 위치와 로봇 링크 결합 정보다. | 큐브와 같은 파일을 쓴다 | 같음 |
| `render.success` | 재생 뒤 성공을 판정할 모듈과 함수, 그리고 결과를 적을 속성 이름이다. | `success_criteria.replay_verdict` | `peg_success_criteria.replay_verdict` |
| `physics.bundle_dir` | 실측 물리 번들 폴더다. `assets/` 아래에서 찾는다. | `fr3_cube_system_calibration_bundle_v1` | `fr3_peg_in_hole_physics_bundle_v1_normalized` |
| `physics.primary_objects` | 번들의 물체 물리를 적용할 장면 물체다. | 큐브 세 개 | 핀 하나 |
| `physics.surface` | 물체가 놓이는 작업면이다. 번들이 작업면과 물체 사이 마찰을 여기에 쓴다. | `work_surface` | `desk_surface` |
| `physics.arm_actuator`, `physics.gripper_actuator` | 팔과 그리퍼 액추에이터 묶음 이름이다. 번들이 그리퍼 힘 배율을 곱할 때 쓴다. | `a1`, `gripper` | `a1`, `h` |
| `physics.object_masses_kg` | 물체별 실측 질량이다(kg). | 큐브 세 개 각각 | 핀 0.0636 |
| `physics.object_size_m` | 관성을 계산할 때 쓰는 대표 변 길이다(m). | 0.0507 | 0.02 |
| `visual.package_dir` | 조명과 색과 카메라 규격이 든 패키지 폴더다. | `fr3_visual_randomization_v1` | 같은 것을 쓴다 |
| `visual.object_prims` | 시각 규격이 부르는 물체 이름을 이 장면의 프림 경로에 잇는 표다. 빈 값이면 이 장면에 없는 물체라는 뜻이다. | 적지 않음(규격 이름과 장면 이름이 같다) | `cube_1`을 핀에 잇고 `cube_2`, `cube_3`은 없음으로 둔다 |
| `dataset.task_string` | 데이터셋에 적을 작업 설명 문장이다. | 큐브 세 개를 탑으로 쌓아라 | 핀을 구멍에 꽂아라 |
| `dataset.robot_type`, `dataset.fps`, `dataset.schema_prefix` | 데이터셋에 적을 로봇 이름과 초당 프레임 수와 형식 이름이다. | `franka_fr3_osc`, 10, `fr3_cube.hf80k` | 같은 로봇과 초당 10개, `fr3_peg.hf80k` |
| `assets.required` | 실행 전 검사가 확인할 파일과 폴더 목록이다. | 시연 파일과 두 패키지 | 시연 파일, 두 패키지, 3D 모델 두 개 |

값을 적지 않으면 환경 코드의 기본값이 그대로 쓰인다. 큐브 프로필은 지금 코드에 박혀 있던
값과 같은 값을 적고 있으므로, 이 배선이 생기기 전과 큐브의 동작이 완전히 같다.

**프로필에 적기만 하고 코드가 읽지 않는 값이 있으면 안 된다.** 값을 고쳐도 아무 일이
일어나지 않고, 고친 사람은 반영됐다고 믿기 때문이다. 실제로 그런 키가 열 개 있었다.
`physics.bundle_dir`을 아무도 읽지 않아서 핀 환경은 실측 물리를 한 줄도 적용하지 않고
돌았고, `render.success`를 아무도 읽지 않아서 렌더가 성공 표시를 남기지 않았으며, 생성과
변환과 렌더를 다 통과한 10편이 기록 단계에서 전부 버려졌다. `src/tests/test_profile_keys_used.py`가
프로필의 모든 키가 코드 어딘가에서 읽히는지 검사한다.

로더는 예외를 던지지 않는다. 파일이 없거나 형식이 틀리면 기본 프로필로 되돌리고 이유를
남긴다. 그리고 실행 전 검사가 "요청한 프로필과 실린 프로필이 다르면" 실행을 거부한다.
조용히 큐브로 되돌아가 엉뚱한 데이터를 만드는 일을 막기 위해서다. 프로필 안의 모르는 키는
경고가 아니라 오류다. 오타 하나가 8만 편을 바꾼다.

설정으로 뺄 수 없는 것도 있다. Isaac 장면 정의와 성공 판정은 태스크마다 코드가 필요하다.
큐브는 `src/env/`, 핀 삽입은 `src/env_peg/`에 있다.

**새 태스크 코드를 쓸 때 반드시 지킬 것이 하나 있다.** 이 컨테이너(Isaac Lab 3.0)는 물체의
회전을 나타내는 네 숫자를 XYZW 순서로 주고받는다. 회전이 없으면 `(0, 0, 0, 1)`이고, FR3
받침의 180도 회전은 `(0, 0, 1, 0)`이다. 자산의 `.data.root_quat_w`도, `isaaclab.utils.math`의
회전 함수도, 시연 파일에 기록된 초기 상태도 전부 이 순서다. Isaac Lab 2.x는 WXYZ였고 3.0에서
바뀌었다.

이것을 반대로 잡으면 실행은 멀쩡히 되고 결과만 전부 실패한다. 실제로 그렇게 만들었다가
697번 시도 동안 로봇이 핀을 한 번도 건드리지 못했다. 회전이 없는 핀이 x축으로 180도 돌아간
것으로 읽혔고, MimicGen은 사람 시연의 물체 자세와 지금 물체 자세의 차이로 손 궤적 전체를
옮기기 때문에 그 180도가 궤적을 엉뚱한 곳으로 보냈다. `src/tests/test_quat_convention.py`가
이 전제를 검사한다. 새 태스크를 붙이면 그 파일에 항목을 더한다.

## 6. 물리 파라미터를 외부에서 받는 방법

코드에는 물리 상수가 하나도 없다. 번들에서 뽑아 만든 `parameters.json`만 읽는다.

받은 번들을 표준 배치로 옮기는 도구가 있다.

```bash
python3 tools/normalize_physics_bundle.py \
    --in  <받은_번들> \
    --out assets/<프로필이_정한_이름> \
    [--dynamics-from <관절_물리를_가져올_번들>]
```

번들마다 모양도 다르고 담고 있는 것도 다르다. 큐브 번들은 `modules/` 아래에 나눠 담고,
핀 삽입 번들은 파일을 최상위에 평평하게 두며 열 이름이 하나도 겹치지 않는다. 도구가 이것을
하나의 표준으로 옮기고, 접촉 값의 이름을 태스크가 아니라 역할로 바꾼다. 큐브의 "큐브끼리"와
핀 삽입의 "핀과 구멍 사이"는 파이프라인 입장에서 똑같이 "주된 접촉 쌍"이다.

없는 값은 채우고 무엇을 했는지 값마다 남긴다. 핀 삽입 번들에는 관절 물리도, 작업면 마찰과
반발도, 물체 감쇠도, 그리퍼 힘 배율도 없다. 로봇과 작업대의 성질이므로 큐브 번들에서
가져오고 `borrowed`로 적는다. 실제로 10개 항목이 그렇게 채워졌다.

```
pair_primary_static_friction   measured:contact.peg_hole.static_friction (confidence low)
object_mass_kg                 measured:object.peg.mass_kg (confidence high)
joint                          borrowed:같은 FR3 로봇이고 두 번들이 같은 제어기 계약 아래에서 맞춰졌다
surface_static_friction        borrowed:이 번들이 재지 않아 기증 번들 값을 쓴다
```

새 번들이 오면 `tools/normalize_physics_bundle.py`의 매핑 표에 한 묶음을 더하면 된다.
파이프라인 코드는 건드리지 않는다.

바꾼 뒤에도 큐브 결과가 달라지지 않는지 확인하는 시험이 있다. 옛 코드와 새 코드의 표본을
같은 시드로 뽑아 비교한다. 세 프로파일 × 세 크기 × 16개 항목이 비트까지 같다.

```bash
python3 src/tests/test_physics_equivalence.py <표준_번들> <옛_코드> <원본_번들>
```

**번들의 값이 어느 장면 물체에 가는지도 프로필이 정한다.** 번들은 "주된 접촉 쌍"이나
"작업면"처럼 역할로 말하고, 그 역할이 이 장면의 어느 물체인지는 태스크마다 다르다. 큐브
쌓기에서 주된 접촉 쌍은 큐브끼리이고 작업면은 `work_surface`다. 핀 삽입에서는 핀과 구멍
사이이고 작업면은 `desk_surface`다. 5절 표의 `physics` 항목이 그 연결이다.

작업면은 운동학 고정 강체여야 한다. Isaac Lab은 강체로 감싼 자산에만 물리 뷰를 만들어
주는데, 번들은 그 뷰를 통해 작업면과 물체 사이 마찰을 쓴다. 충돌만 있는 프림으로 두면 접촉
쌍의 작업면 쪽에 손댈 방법이 없어 마찰 보정이 조용히 사라진다. 운동학 고정으로 두면 중력도
접촉 충격량도 받지 않으므로 고정된 책상으로 그대로 동작한다. 두 태스크 모두 이렇게 되어
있다.

## 7. 모듈로 쓰는 방법

**단계 하나만 부르기.** 다섯 단계를 따로 실행할 수 있다. 무엇이 들어가고 나오는지는
`--io`로 본다.

```bash
python3 src/stage.py --io
python3 src/stage.py generate --chunk-dir /work/c0 --episodes 50 --seed 42000
python3 src/stage.py convert  --chunk-dir /work/c0
python3 src/stage.py render   --chunk-dir /work/c0 --profile nominal_lab
python3 src/stage.py lerobot  --chunk-dir /work/c0 --profile nominal_lab
python3 src/stage.py upload   --chunk-dir /work/c0 --chunk-index 0
```

**허깅페이스 없이 돌리기.** `.env`에 `HF_UPLOAD=0`을 두면 업로드를 하지 않고 실행 전
검사도 자격증명을 보지 않는다. 결과는 작업 디렉터리에만 쌓인다.

**중간 산출물 남기기.** `KEEP_INTERMEDIATE=1`을 두면 청크가 끝나도 `gen.hdf5`,
`contract.hdf5`, `rgb.hdf5`를 지우지 않는다. 청크마다 수십 GB가 쌓인다.

## 8. 실측값

L40S 한 장에서 큐브 100편을 끝까지 돌려 잰 값이다. `NUM_ENVS=16`, 생성 프로세스 1개,
렌더 프로세스 2개, 물리 랜덤화를 켠 상태다.

| 청크 | 프로파일 | 편수 | 시도 | 수율 | 편당 |
|---|---|---:|---:|---:|---:|
| 0 | nominal_lab | 50 | 402 | 12.4% | 34.1초 |
| 1 | lab_variation | 40 | 349 | 11.5% | 34.8초 |
| 2 | stress_tail | 10 | 83 | 12.0% | 46.0초 |

완성된 데이터는 편당 약 0.87 MB다. 100편이 86.7 MB로 올라갔다. 8만 편이면 약 70 GB다.

편당 34초로 8만 편을 계산하면 GPU 한 장에 31.5일, 네 장에 7.9일이다. 이 값은 100편
실행을 늘린 추정이다. 본 실행은 청크가 500편이라 시뮬레이터를 띄우는 비용이 편당 더 적게
들어가므로 이보다 짧아진다.

물리 랜덤화를 켜도 수율이 떨어지지 않는다. 끄고 잰 값이 15.2%, 켜고 잰 값이 11.5%에서
14.2% 사이이고, 차이가 통계적으로 유의하지 않다.

### 핀 삽입 수율

핀 삽입은 큐브와 성질이 다르다. 핀과 구멍 사이 틈이 0.66 mm에서 1.16 mm뿐이라 손끝이
조금만 어긋나도 테두리에 걸린다. 그래서 두 가지가 큐브와 다르게 작동한다.

**매 스텝 명령에 더하는 잡음을 넣으면 성공이 0이 된다.** 큐브는 잡음 0.03을 쓴다. 같은
시연에서 서로 다른 궤적이 나오게 하려는 것이다. 핀 삽입에서 같은 값을 쓰면 핀이 구멍 축에서
1.6 mm까지 다가가고도 23도 기울어진 채 테두리에 얹힌다. 잰 값은 아래와 같다.

| 명령 잡음 | 시도 | 성공 | 수율 |
|---:|---:|---:|---:|
| 0.03 | 697 | 0 | 0% |
| 0.01 | 40 | 0 | 0% |
| 0.0 | 48 | 20 | 41.7% |

**수율이 실행마다 크게 흔들린다.** 씨앗값 7로 잰 값이 41.7%(20/48)였고 씨앗값 51000으로 잰
값이 13.0%(3/23)였다. 두 실행의 설정은 씨앗값 말고 같다. 소스 시연이 4편뿐이라 MimicGen이
구간마다 고를 수 있는 궤적이 적고, 그래서 어떤 배치를 뽑느냐에 따라 결과가 크게 달라지는
것으로 보인다. 확정하려면 씨앗값을 바꿔 가며 여러 번 재야 한다. 8만 편 일정을 잡을 때는
낮은 쪽인 13%를 기준으로 삼는 것이 안전하다.

## 9. 알려진 한계

**핀 삽입은 명령 잡음을 넣을 수 없어 궤적 다양성이 큐브보다 낮다.** 8절에 적었듯이 잡음을
0.01만 넣어도 성공이 0이 된다. 그래서 핀 삽입에서 에피소드마다 달라지는 것은 핀의 시작
위치와 물리 값과 조명·색·카메라뿐이고, 같은 배치에서 손이 지나가는 길은 사실상 같다.
큐브는 잡음 0.03이 손이 지나가는 길 자체를 매번 다르게 만든다. 정책 학습에 쓸 때 이 차이를
염두에 두어야 한다.

**핀 삽입의 소스 시연은 4편뿐이다.** 큐브는 13편이고 그중 12편이 쓰인다. 소스가 적으면
생성된 데이터가 원본 4편의 변형에 머문다. 표시가 붙은 시연을 더 확보하는 것이 다양성을
올리는 가장 직접적인 방법이다.

**표시가 없는 시연으로는 아직 핀 삽입을 시작할 수 없다.** 어노테이션 단계를 파이프라인
안으로 들였지만, 서버의 `peg_source.hdf5`(12편)로는 표시를 붙일 수 없다. 그 파일의
`actions`가 그 파일 자신의 궤적을 만들어 낸 명령이 아니기 때문이다. 명령이 정확히 0인
235스텝 동안 손끝이 0.51 m 움직인다. 재생이 삽입을 재현하지 못하므로 어노테이션이 12편
모두 실패한다. 그래서 이미 표시가 붙어 있는 4편(`peg_annotated.hdf5`)을 쓰고 있다.

**핀과 구멍 사이 틈을 반영하지 못한다.** 핀 삽입 번들의 대표 값인
`task.peg_hole.radial_clearance_m`(0.66 mm에서 1.16 mm)은 재질이 아니라 형상이다. 지금
물리 항은 질량과 관성과 무게중심과 재질만 바꾸고 물체 크기는 건드리지 않는다. 값은
`parameters.json`에 실려 있으나 적용되지 않는다.

**시각 랜덤화의 커튼 두 개는 넣지 못한다.** 규격에 색과 재질은 있으나 3D 모델이 없다.
건너뛴 항목으로 매 에피소드 기록된다.
