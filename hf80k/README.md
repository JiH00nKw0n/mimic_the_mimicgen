# FR3 로봇 합성 데이터 생성 파이프라인

사람이 로봇을 조종해 녹화한 시연 몇 편을 넣으면, 물체 위치와 조명과 물리 성질이 서로 다른
성공 에피소드를 원하는 개수만큼 만들어 허깅페이스에 데이터셋으로 올린다. 도커 컨테이너
하나가 처음부터 끝까지 수행한다. 2026-08-24 기준으로 적었다.

읽는 순서를 먼저 말한다. 무엇을 넣고 무엇이 나오는지 알고 싶으면 1장과 2장을 읽는다.
직접 돌리려면 3장과 4장을 읽는다. 안에서 무슨 일이 일어나는지 알고 싶으면 5장을 읽는다.
다른 작업으로 바꾸려면 6장을, 지금 안 되는 것을 알려면 8장을 읽는다.

## 목차

1. [지금 어디까지 되는가](#1-지금-어디까지-되는가). 두 작업이 각각 어느 단계까지 확인됐고 결과물이 어디에 있는지 적었다.
2. [무엇을 넣고 무엇이 나오는가](#2-무엇을-넣고-무엇이-나오는가). 입력 파일 하나하나의 정체와 출력 데이터셋의 내용을 적었다.
3. [준비물](#3-준비물). 필요한 하드웨어와 파일과 계정을 적었다.
4. [실행 방법](#4-실행-방법). 명령을 순서대로 적고 각 명령이 무엇을 하는지 적었다.
5. [내부에서 일어나는 일](#5-내부에서-일어나는-일). 단계마다 무엇을 읽어 무엇을 쓰는지 적었다.
6. [다른 작업으로 바꾸는 방법](#6-다른-작업으로-바꾸는-방법). 설정 파일 한 장이 정하는 값을 전부 표로 적었다.
7. [실제로 잰 값](#7-실제로-잰-값). 시간과 성공률과 용량을 측정치로 적었다.
8. [지금 안 되는 것](#8-지금-안-되는-것). 확인하지 못한 것과 한계를 적었다.
9. [문제가 생겼을 때](#9-문제가-생겼을-때). 실제로 겪은 실패와 각각의 원인을 적었다.

## 1. 지금 어디까지 되는가

구간 표시가 붙은 시연을 넣으면 허깅페이스 데이터셋이 나오는 데까지 두 작업 모두 확인했다.
여기서 구간 표시란 시연 안에서 어디까지가 집는 동작이고 어디부터가 놓는 동작인지를 적어
둔 것이고, 2장에서 자세히 설명한다.

| 항목 | 큐브 세 개 쌓기 | 핀을 구멍에 꽂기 |
|---|---|---|
| 설정 파일 이름 | `cube_stack_fr3` | `peg_insert_fr3` |
| 실행 전 검사 16개 | 통과 | 통과 |
| 새 에피소드 생성 | 확인함. 성공률 12.4% | 확인함. 성공률 8.2% |
| SART 증강 | 꺼짐 | 켜짐. 증강 성공률 5.0%에서 14.8% 사이 |
| 명령 형식 변환 | 확인함 | 확인함 |
| 카메라 영상 만들기 | 확인함 | 확인함 |
| 데이터셋 기록 | 확인함 | 확인함 |
| 허깅페이스 업로드 | 확인함 | 확인함 |
| 실측 물리값 반영 | 적용됨 | 적용됨 |
| 만들어 둔 데이터셋 | 100편, 17,669프레임 | 30편, 3,060프레임 |
| 주소 | https://huggingface.co/datasets/Mayfull/robot-test | https://huggingface.co/datasets/Mayfull/robot-test-peg |

세 데이터셋 모두 공개다. 비공개로 만들면 허깅페이스의 데이터 미리보기 화면에서 열리지
않는데, 그 화면이 로그인 없이 데이터를 가져가기 때문이다. `.env`의 `HF_PRIVATE`가 공개
여부를 정한다.

핀 꽂기에는 SART 증강을 켠 데이터셋이 하나 더 있다. 주소는
https://huggingface.co/datasets/Mayfull/robot-test-peg-sart 이고, 같은 시연 4편에서
MimicGen이 만든 편과 SART가 접근 구간을 다시 만든 편을 섞어 담는다. SART가 무엇인지는
5장에 적었다.

핀 꽂기는 오랫동안 성공이 하나도 나오지 않다가 2026-08-23에 동작하게 됐다. 원인 두 가지를
7장에 측정값과 함께 적었다.

## 2. 무엇을 넣고 무엇이 나오는가

### 넣는 것

파일 네 종류와 설정 한 장이다. 파일은 전부 `hf80k/assets/` 폴더에 놓는다.

**첫째, 구간 표시가 붙은 시연 파일.** 가장 중요한 입력이다.

사람이 조종기로 로봇을 움직여 작업을 한 번 해내면 그 과정이 HDF5 파일 한 편으로 남는다.
HDF5는 배열 여러 개에 이름표를 붙여 한 파일에 담는 형식이다. 한 편에는 매 시점의 관절
각도와 손끝 위치와 로봇에게 준 명령이 시간 순서대로 들어 있다.

이 파일만으로는 새 에피소드를 만들 수 없다. 생성기가 "이 시연에서 집는 동작만 떼어다가
물체가 다른 자리에 있는 새 장면에 옮겨 붙인다"는 방식으로 작동하기 때문에, 시연 안에서
동작이 바뀌는 지점이 어디인지 알아야 한다. 그 지점을 적어 둔 것이 구간 표시이고, 파일 안
`obs/datagen_info/subtask_term_signals` 자리에 들어 있다.

큐브 쌓기의 시연 파일은 `fwd_annotated.hdf5`이고 13편이 들어 있다. 표시는 세 가지다.
`grasp_1`은 첫 큐브를 집은 시점, `stack_1`은 그것을 두 번째 큐브 위에 올린 시점,
`grasp_2`는 세 번째 큐브를 집은 시점이다. 한 편이 202스텝에서 382스텝 사이이고 13편을
합쳐 4,174스텝이다.

핀 꽂기의 시연 파일은 `peg_annotated.hdf5`이고 4편이 들어 있다. 표시는 `grasp_peg`
하나뿐이다. 핀을 집은 시점이다.

**표시가 없는 녹화 원본에서 시작한다면 `make prepare`를 먼저 한 번 돌린다.** 그 명령이
녹화 원본을 시뮬레이터에서 다시 재생해 작업에 성공한 편만 남기고, 남은 편에 구간 표시를
붙인다. 4장에 명령이 있고 5장에 무슨 일이 일어나는지 적었다.

**둘째, 실측 물리값 묶음.** 실제 로봇과 실제 물체를 재서 얻은 숫자들이 폴더 하나에 들어
있다. 물체의 무게, 물체끼리의 마찰, 물체와 작업면 사이의 마찰, 관절의 마찰, 그리퍼가 내는
힘의 배율 같은 값이다. 값마다 하나의 숫자가 아니라 여러 벌이 들어 있어서 에피소드마다 한
벌을 뽑아 쓴다. 그래서 만들어진 데이터가 하나의 고정된 물리가 아니라 실제로 측정된 범위
안의 여러 물리를 담는다.

큐브 쌓기는 `fr3_cube_system_calibration_bundle_v1`을, 핀 꽂기는
`fr3_peg_in_hole_physics_bundle_v1_normalized`를 쓴다.

**셋째, 시각 조건 규격 묶음.** 조명의 색과 밝기, 물체와 책상의 색과 거칠기, 카메라의
위치와 각도가 에피소드마다 얼마나 달라져도 되는지를 적어 둔 폴더다. 두 작업이 같은
`fr3_visual_randomization_v1`을 쓴다.

**넷째, 3D 모델 파일.** 핀 꽂기에만 필요하다. 책상과 구멍의 모양을 담은
`peg_hole_env.usd`와 `hole_01.usd` 두 개다. 큐브는 상자 모양이라 코드가 직접 만들어 낸다.

**다섯째, `.env` 설정 파일.** 허깅페이스 토큰과 저장소 이름, 만들 에피소드 개수, 어느
작업으로 돌릴지를 적는다. `.env.example`을 복사해 채운다.

### 나오는 것

허깅페이스 저장소 하나에 LeRobot v3 형식의 데이터셋이 올라간다. LeRobot은 로봇 학습용
데이터를 담는 공개 형식이고 v3는 그중 최신 판이다.

에피소드 하나는 시간 순서로 늘어선 프레임의 나열이고, 프레임 하나에 다음이 들어 있다.

| 이름 | 내용 | 크기 |
|---|---|---|
| `observation.images.third_person_0` | 작업 전체를 비추는 카메라 영상 | 세로 180, 가로 320, 색 3채널 |
| `observation.images.third_person_1` | 다른 각도에서 비추는 카메라 영상 | 같음 |
| `observation.images.wrist` | 로봇 손목에 달린 카메라 영상 | 같음 |
| `observation.state` | 로봇의 현재 상태를 적은 숫자 | 23개 |
| `action` | 그 시점에 로봇에게 준 명령 | 7개 |
| `visual.profile_id` | 이 에피소드에 적용한 시각 조건 묶음의 번호 | 1개 |

`observation.state`의 숫자 23개는 세 덩어리다. 앞의 9개는 관절 9개의 각도이고, 다음 7개는
손끝의 위치 세 개와 방향 네 개이며, 마지막 7개는 바로 직전 시점에 준 명령이다. 첫
프레임에는 직전 명령이 없으므로 0으로 채운다.

`action`의 숫자 7개는 손끝을 어느 방향으로 얼마나 옮길지 세 개, 어느 축으로 얼마나 돌릴지
세 개, 그리퍼를 열지 닫을지 한 개다.

초당 10프레임이다. 영상과 명령이 같은 10프레임에 맞춰져 있다.

저장소에는 `meta/info.json`도 함께 올라간다. 에피소드 총 개수와 프레임 총 개수와 각
항목의 크기가 적힌 파일이고, 학습 코드가 이 파일을 먼저 읽는다.

## 3. 준비물

**하드웨어.** NVIDIA GPU 한 장 이상과 도커. GPU 메모리는 24 GB 이상을 권한다. 개발과
측정은 L40S 48 GB 한 장, vCPU 8개, 메모리 61 GB인 기계에서 했다.

생성 단계는 물리 계산을 CPU에서 돌리므로 실제 병목이 GPU가 아니라 CPU 코어 수다. 카메라
영상을 만드는 단계만 GPU를 쓴다. vCPU 8개 기계에서 렌더를 두 개 동시에 돌리면 부하가
21을 넘어 서로 느려진다.

**디스크.** 중간 파일이 청크마다 수십 GB 쌓였다가 지워진다. 8만 편을 만들려면 여유
400 GB를 권한다. 최종 데이터는 편당 약 0.44 MB에서 0.87 MB다.

**파일.** 2장에 적은 자산을 `hf80k/assets/`에 놓는다. 다른 기계에서 가져오려면
`make assets FROM=<ssh 별칭이나 경로>`를 쓴다.

**계정.** 허깅페이스 쓰기 토큰이 필요하다. 이미지에 굽지 않고 실행할 때 `.env`로만
넣는다. `.env`는 git에 올라가지 않는다.

## 4. 실행 방법

전부 `hf80k` 폴더 안에서 실행한다.

### 처음 한 번

```bash
cp .env.example .env      # 허깅페이스 토큰과 저장소 이름을 채운다
make check                # 자산과 .env가 갖춰졌는지 본다
make build                # 도커 이미지를 굽는다. 처음에는 30분에서 40분
```

`make check`는 파일이 있는지, `.env`의 필수 값이 채워졌는지, 도커가 도는지를 본다. 이미지를
굽는 데 오래 걸리는 이유는 Isaac Sim 기본 이미지가 크고 그 위에 파이썬 꾸러미를 더 깔기
때문이다. 두 번째부터는 바뀐 부분만 다시 구워서 몇 초에 끝난다.

### 표시가 없는 녹화 원본에서 시작한다면

```bash
make prepare IN=/절대경로/raw.hdf5 OUT=$(pwd)/assets/fwd_annotated.hdf5
```

시뮬레이터에서 다시 재생해 성공한 편만 남긴 뒤 구간 표시를 붙인다. 파이프라인을 돌리기
전에 한 번만 하면 된다. 이미 걸러진 파일이면 재생을 건너뛴다.

```bash
make annotate IN=/절대경로/filtered.hdf5 OUT=$(pwd)/assets/fwd_annotated.hdf5
```

### 동작 확인과 본 실행

```bash
make smoke                # 100편으로 끝까지 한 번 돌려 본다
make run                  # 본 실행. .env의 TARGET_EPISODES 만큼 만든다
make aggregate WORK=...   # 끝나면 청크를 하나로 합쳐 최상위에 올린다
```

`make smoke`는 결과를 별도 폴더에 쌓아서 본 실행과 섞이지 않는다. GPU 한 장에서 약 한
시간 걸린다.

**마지막 합치기를 빼먹으면 안 된다.** 청크는 만들어질 때마다 저장소의
`chunks/chunk_00000` 같은 자리에 따로 올라간다. 그 상태에서는 저장소 최상위에
`meta/info.json`이 없어서 허깅페이스 화면과 학습 코드가 데이터셋을 찾지 못한다.
`make aggregate`가 청크를 합쳐 최상위에 올리고 데이터셋 설명 카드도 같이 쓴다.

### GPU 여러 장

```bash
make run-4gpu
make aggregate WORK='/data/hf80k/gpu*'
```

컨테이너 네 개가 각각 5분의 1씩 맡는다. 합칠 때 작업 디렉터리를 전부 넘겨야 한다. 하나만
넘기면 4분의 1만 담긴 데이터셋이 오류 없이 만들어진다.

### 다른 작업으로 돌리기

`.env`에 한 줄을 더한다.

```
TASK_PROFILE=peg_insert_fr3
```

### 진행 상황 보기

```bash
make logs        # 컨테이너 로그를 따라간다
make progress    # 청크 몇 개가 끝났는지 센다
make state       # 지금 계획과 진행 상황을 본다
make stop        # 컨테이너를 멈춘다. 끝난 청크는 남으므로 이어서 할 수 있다
```

## 5. 내부에서 일어나는 일

에피소드를 정해진 개수씩 묶어 청크 단위로 만든다. 청크 하나가 끝나면 바로 허깅페이스에
올리고 중간 파일을 지운다. 그래야 8만 편을 만드는 동안 디스크가 넘치지 않는다. 중간에
멈춰도 끝난 청크는 건너뛰고 이어서 한다.

### 전체 흐름

```
[준비]  make prepare 로 한 번만. 파이프라인 밖이다.
  녹화 원본
    ↓ 다시 재생해 성공한 편만 남긴다
    ↓ 구간 표시를 붙인다
  표시가 붙은 시연

[본 실행]  청크마다 반복한다.
  표시가 붙은 시연
    0. 소스 고르기   성공률 0인 시연을 뺀 사본을 만든다
    1. 생성          새 배치에서 성공한 궤적만 남긴다
    2. SART 증강     접근 구간만 다시 만들어 편수를 늘린다 (선택)
    3. 변환          실기가 받는 명령 형식으로 바꾼다
    4. 렌더          카메라 세 대의 영상을 만든다
    5. 기록          LeRobot 데이터셋으로 쓴다
    6. 업로드        허깅페이스에 올린다
```

### 준비 단계

**다시 재생해 성공한 편만 남긴다.** 녹화 파일에는 매 시점의 관절 각도와 로봇에게 준
명령이 들어 있다. 사람이 실제로 작업을 해냈으니 그 파일은 성공한 시연이다. 그런데 같은
명령을 시뮬레이터에서 다시 실행한다고 해서 같은 결과가 나오지는 않는다. 녹화할 때와 재생할
때의 물리 계산이 조금씩 달라 손끝 위치가 서서히 어긋나기 때문이다. 어긋남이 쌓이면 물체를
놓치거나 탑이 무너진다.

이 단계는 시연 한 편마다 녹화된 첫 상태로 장면을 되돌리고, 녹화된 명령을 한 스텝씩 그대로
실행하고, 마지막 상태를 보고 성공을 판정한다. 성공한 편만 남긴다. 판정 방법은 작업마다
다르므로 설정 파일이 정한다.

**구간 표시를 붙인다.** Isaac Lab이 제공하는 표시 도구를 컨테이너 안에서 돌린다. 도구가
궤적을 훑으며 물체를 집은 시점과 놓은 시점을 찾아 신호로 적는다.

이 도구는 **표시에 성공한 편수를 종료 코드로 돌려준다.** 12편을 다 성공하면 12로 끝난다.
보통의 "0이면 성공" 규칙으로 판정하면 성공이 실패로 뒤집힌다. 그래서 종료 코드가 아니라
만들어진 파일을 열어 판정한다.

### 0단계. 소스 고르기

시연 중에 새 에피소드를 한 번도 만들어 내지 못한 것이 있으면 뺀다. 어느 시연이 그런지는
`assets/source_yield.json`에 측정치로 적혀 있다. 실제로 큐브 13편 중 1편이 37번 시도에
성공 0이었다. 빼면 성공률이 12.4%에서 15.2%로 오른다.

이 단계는 걸러 낸 사본을 실제로 만든다. 표시만 해 두는 방식으로는 걸러지지 않는다.
생성기가 파일에 있는 시연을 전부 후보로 삼고 표시를 보지 않기 때문이다.

**입력** 표시가 붙은 시연, 성공률 측정치 **출력** `source_filtered.hdf5`

### 1단계. 생성

Isaac Sim 안에서 MimicGen이 돈다. 시연 하나를 고르고, 장면의 물체를 새 위치에 무작위로
놓고, 그 시연의 구간별 손끝 궤적을 새 위치에 맞게 옮겨 이어 붙인 뒤, 물리를 실제로 돌려
본다. 성공이면 저장하고 아니면 버린다.

성공의 정의는 작업마다 다르다. 큐브 쌓기는 세 개가 탑으로 서고 그리퍼가 손을 뗐는지 본다.
핀 꽂기는 핀이 구멍 축에서 1 cm 안에, 깊이 2 cm 이상, 똑바로 꽂혔는지 본다.

물리는 매번 같지 않다. 실측 물리값 묶음에서 한 벌을 뽑아 그 시도의 물리로 넣는다. 마찰,
질량, 관성, 무게중심, 그리퍼 힘 배율이 에피소드마다 달라진다.

**입력** `source_filtered.hdf5` **출력** `gen.hdf5`(성공 궤적만, 초당 20스텝),
`gen.provenance.json`(어느 시연에서 몇 번 시도해 몇 번 성공했는지)

### 2단계. SART 증강 (선택)

성공한 궤적 한 편에서 여러 편을 만들어 낸다. 핀 꽂기에서 기본으로 켜져 있고 큐브 쌓기에서는
꺼져 있다. 꺼져 있으면 이 단계가 첫 문장에서 그대로 돌아 나온다.

궤적 하나를 세 토막으로 본다. 물체를 집어 목표 위까지 옮기는 운반 구간, 그 뒤 마지막으로
자세를 맞추는 접근 구간, 그리고 실제로 밀어 넣는 삽입 구간이다. 운반 구간과 삽입 구간은
한 숫자도 건드리지 않고 그대로 복사하고, 가운데 접근 구간만 새로 만든다.

새로 만드는 방법은 이렇다. 원본이 삽입을 시작하는 자세를 중심으로 반지름 6 cm짜리 공을
그리고 그 안에서 자세를 하나 무작위로 뽑는다. 손을 그 자세까지 옮겼다가, 거기서 원본의
삽입 시작 자세로 한 방향으로 되돌아온다. 되돌아오는 도중에 다시 멀어지지 않는다. 그다음은
원본의 삽입 명령을 그대로 재생한다.

이렇게 하는 이유는 핀 꽂기의 성질 때문이다. 핀과 구멍 사이 틈이 0.66 mm에서 1.16 mm뿐이라
삽입 구간에서는 조금만 어긋나도 실패한다. 접근 구간은 여유가 있다. 여유가 있는 곳에서만
다양성을 얻고 없는 곳에서는 원본을 그대로 쓴다.

**증강이 제대로 됐는지는 성공률로 알 수 없다.** 증강이 무너져서 원본을 그대로 복사하면
원본이 이미 성공한 궤적이니 복사본도 전부 성공해서 성공률이 오히려 100%에 가까워진다.
대신 같은 원본에서 나온 편들끼리 손끝 좌표가 얼마나 다른지를 구간별로 잰다. 접근 구간이
삽입 구간보다 몇 배 흩어져 있는지가 판단 기준이고, 이 값이 3배 아래로 내려가면 실행 기록에
경고를 적는다. 실제로 잰 값은 202배와 205.8배였다.

**입력** `gen.hdf5` **출력** `gen_sart.hdf5`(생성분과 증강분을 묶은 파일),
`sart_report.json`(시도 횟수, 성공 수, 다양성 측정치)

### 3단계. 변환

관절 각도에서 손끝 자세를 계산하고, 초당 20스텝을 초당 10스텝으로 다시 뽑고, 실기가 받는
명령 형식으로 바꾼다. 이 단계는 시뮬레이터를 손끝 자세 계산에만 쓰고 물리를 돌리지 않는다.

**입력** `gen.hdf5` 또는 `gen_sart.hdf5` **출력** `contract.hdf5`,
`contract_report.json`

### 4단계. 렌더

궤적을 다시 재생하면서 카메라 세 대로 찍는다. 카메라 위치는 실기를 측정한 값에서 온다.
에피소드마다 조명과 색과 카메라 각도를 다시 뽑는다.

**여기서 성공 판정을 한 번 더 한다.** 같은 명령을 물리와 함께 다시 돌렸을 때도 같은 결과가
나오는지 보는 것이라, 생성 단계 판정과 독립적인 두 번째 관문이다.

**입력** `gen.hdf5` 또는 `gen_sart.hdf5`, 시각 규격 **출력** `rgb.hdf5`(영상과 재생 성공
판정), `vrand_log.json`(에피소드마다 실제로 적용된 값)

### 5단계. 기록

명령과 영상을 합쳐 LeRobot 데이터셋으로 쓴다. 둘을 붙일 때 프레임 번호가 아니라 시간으로
맞춘다. 두 길이가 한 프레임쯤 다를 수 있는데, 번호로 맞추면 그때 에피소드를 통째로 버리게
된다.

**여기서 성공 판정을 세 번째로 확인한다.** 생성 단계 판정과 재생 단계 판정이 둘 다 표시돼
있어야 기록한다. 표시가 없으면 통과가 아니라 거부로 처리한다. 판정이 돌지 않은 경우가
조용히 성공으로 섞이지 않게 하려는 것이다.

**입력** `contract.hdf5`, `rgb.hdf5`, `vrand_log.json` **출력** `lerobot/` 폴더

### 6단계. 업로드

청크 하나를 저장소의 자기 자리에 올린다. 컨테이너마다 다른 이름을 쓰므로 GPU 여러 장으로
돌려도 서로 덮어쓰지 않는다. 마지막에 `make aggregate`가 전부 합쳐 최상위에 올린다.

설정 파일이 정하는 값을 전부 적으면 아래와 같다. 같은 뜻의 환경변수를 밖에서 주면 그쪽이

값을 적지 않으면 코드의 기본값이 쓰인다. 큐브 설정 파일은 지금 코드에 박혀 있던 값과 같은
값을 적고 있으므로, 이 배선이 생기기 전과 큐브의 동작이 완전히 같다.

**설정 파일에 적기만 하고 코드가 읽지 않는 값이 있으면 안 된다.** 값을 고쳐도 아무 일이
일어나지 않고, 고친 사람은 반영됐다고 믿기 때문이다. 실제로 그런 키가 열 개 있었다.
`physics.bundle_dir`을 아무도 읽지 않아서 핀 환경은 실측 물리를 한 줄도 적용하지 않고
돌았고, `render.success`를 아무도 읽지 않아서 렌더가 성공 표시를 남기지 않았으며, 생성과
변환과 렌더를 다 통과한 10편이 기록 단계에서 전부 버려졌다.
`src/tests/test_profile_keys_used.py`가 모든 키가 코드 어딘가에서 읽히는지 검사한다.

설정으로 뺄 수 없는 것도 있다. 시뮬레이터 장면 정의와 성공 판정 계산은 작업마다 코드가
필요하다. 큐브는 `src/env/`, 핀 꽂기는 `src/env_peg/`에 있다.

**새 작업 코드를 쓸 때 반드시 지킬 것이 하나 있다.** 이 컨테이너는 물체의 회전을 나타내는
네 숫자를 XYZW 순서로 주고받는다. 회전이 없으면 `(0, 0, 0, 1)`이고 로봇 받침의 180도
회전은 `(0, 0, 1, 0)`이다. Isaac Lab 2.x는 WXYZ였고 3.0에서 바뀌었다. 이것을 반대로 잡으면
실행은 멀쩡히 되고 결과만 전부 실패한다. 실제로 그렇게 만들었다가 697번 시도 동안 로봇이
핀을 한 번도 건드리지 못했다. `src/tests/test_quat_convention.py`가 이 전제를 검사한다.

## 7. 실제로 잰 값

전부 L40S 한 장, vCPU 8개인 기계에서 잰 값이다. 추정이 아니라 실행 기록에서 읽은 숫자다.

### 큐브 세 개 쌓기, 100편

`NUM_ENVS=16`, 생성 프로세스 1개, 렌더 프로세스 2개, 물리값 무작위 뽑기를 켠 상태다.

| 청크 | 시각 조건 | 편수 | 시도 | 성공률 | 편당 시간 |
|---|---|---:|---:|---:|---:|
| 0 | 기본 | 50 | 402 | 12.4% | 34.1초 |
| 1 | 변화 | 40 | 349 | 11.5% | 34.8초 |
| 2 | 극단 | 10 | 83 | 12.0% | 46.0초 |

완성된 데이터는 편당 약 0.87 MB다. 100편이 86.7 MB로 올라갔고 8만 편이면 약 70 GB다.

편당 34초로 8만 편을 계산하면 GPU 한 장에 31.5일, 네 장에 7.9일이다. 이 값은 100편 실행을
늘린 추정이다. 본 실행은 청크가 500편이라 시뮬레이터를 띄우는 비용이 편당 더 적게 들어가므로
이보다 짧아진다.

물리값을 매번 다시 뽑아도 성공률이 떨어지지 않는다. 고정하고 잰 값이 15.2%, 다시 뽑고 잰
값이 11.5%에서 14.2% 사이이고 차이가 통계적으로 유의하지 않다.

### 큐브 회귀 확인, 6편

핀 꽂기를 고치면서 두 작업이 함께 쓰는 파일 일곱 개를 건드렸다. 변환, 형식 검사, 렌더,
성공 판정, 시각 조건, 큐브 환경 설정, 실행 관리자다. 큐브가 그대로인지 6편을 끝까지 돌려
확인했다.

| 청크 | 시각 조건 | 편수 | 시도 | 성공률 | 프레임 |
|---|---|---:|---:|---:|---:|
| 0 | 기본 | 3 | 22 | 13.6% | 528 |
| 1 | 변화 | 2 | 21 | 9.5% | 352 |
| 2 | 극단 | 1 | 17 | 5.9% | 176 |

세 청크가 모두 통과했고 실패가 없다. 성공률은 편수가 적어 흔들리지만 100편 실행의 12.4%
범위 안이다.

### 핀 꽂기, 30편

물리값을 매번 다시 뽑고 SART를 끈 상태다. `NUM_ENVS=4`, 렌더 프로세스 2개다.

약 65초다. 완성된 데이터는 편당 약 0.44 MB이고 30편이 13.3 MB로 올라갔다.

### 핀 꽂기에 SART를 적용한 결과, 44편

같은 조건에 SART를 켜고 `source_frac`을 1.0으로 둔 실행이다. 생성이 목표 30편을 다 만들고
증강분이 그 위에 더해져 44편이 됐다.

| 청크 | 생성 | 증강 | 합계 | 증강 시도 | 증강 성공률 | 다양성 대비 |
|---|---:|---:|---:|---:|---:|---:|
| 0 | 10 | 3 | 13 | 60 | 5.0% | 205.8배 |
| 1 | 10 | 5 | 15 | 60 | 8.3% | 523.0배 |
| 2 | 3 | 3 | 6 | 18 | 16.7% | 479.5배 |
| 3 | 5 | 3 | 8 | 30 | 10.0% | 잴 수 없음 |
| 4 | 2 | 0 | 2 | 돌지 않음 | | |
| 합계 | 30 | 14 | 44 | 168 | 8.3% | |

다양성 대비는 접근 구간이 삽입 구간보다 몇 배 흩어져 있는지다. 3번과 4번 청크에서 "잴 수
없음"인 이유는 같은 원본에서 두 편 이상 성공해야 편들끼리 비교가 되는데 그러지 못했기
때문이다. 0으로 적지 않는다. 0은 증강이 원본 복사로 무너졌다는 뜻이고 여기는 잴 수 없다는
뜻이라, 두 경우를 같은 숫자로 적으면 무너진 실행을 놓친다.

물리값을 고정하고 원본 9편으로 따로 잰 값은 이렇다. 61회 시도에 9편 성공(14.8%), 접근 구간
표준편차 17.6 mm, 삽입 구간 0.087 mm, 대비 202배다.

### 핀 꽂기의 두 가지 성질

핀과 구멍 사이 틈이 0.66 mm에서 1.16 mm뿐이라 손끝이 조금만 어긋나도 테두리에 걸린다.
그래서 두 가지가 큐브와 다르게 작동한다.

**매 스텝 명령에 잡음을 더하면 성공이 0이 된다.** 큐브는 잡음 0.03을 쓴다. 같은 시연에서
서로 다른 궤적이 나오게 하려는 것이다. 핀 꽂기에서 같은 값을 쓰면 핀이 구멍 축에서
1.6 mm까지 다가가고도 23도 기울어진 채 테두리에 얹힌다. 물리를 고정하고 잰 값이다.

| 명령 잡음 | 시도 | 성공 | 성공률 |
|---:|---:|---:|---:|
| 0.03 | 697 | 0 | 0% |
| 0.01 | 40 | 0 | 0% |
| 0.0 | 48 | 20 | 41.7% |

**물리값을 매번 다시 뽑으면 성공률이 내려간다.** 씨앗값을 고정하고 물리 항만 켜고 껐다.
고정한 경우 41.7%(20/48), 매번 다시 뽑는 경우 16.1%(9/56)였다. 마찰이 달라지면 핀을 쥔
자세가 달라지고, 0.7 mm 틈에서는 그 차이가 그대로 실패가 된다. 큐브에서는 이런 차이가
나타나지 않았다.

8만 편 일정을 잡을 때는 물리값을 다시 뽑는 조건의 낮은 쪽인 8%를 기준으로 삼는 것이
안전하다. 같은 편수를 얻는 데 큐브보다 시도가 약 1.5배 필요하다는 뜻이다.

## 8. 지금 안 되는 것

### 녹화 원본에서 시작하는 경로

`make prepare`가 두 단계를 컨테이너 안에서 수행한다. 다시 재생해 성공한 편만 남기는 것과
구간 표시를 붙이는 것이다. 두 단계 모두 컨테이너 안에서 도는 것을 확인했다. 다만 아래
세 가지가 남아 있다.

**녹화 파일이 다른 시뮬레이터 환경에서 만들어진 것이면 그 앞에 한 단계가 더 필요하다.**
지금 서버에 있는 녹화 원본 두 개가 그런 경우다. 수집 환경의 이름이
`OmniReset-Fr3Panda-RelCartesianOSC-State-Play-v0`이고 물체 이름이
`insertive_object`, `receptive_object`, `table`인데, 우리 장면은 `peg`, `desk_surface`를
쓴다. 이름부터 다르니 그대로 되돌릴 수 없다.

`make prepare`를 그런 파일에 돌리면 지금은 이렇게 말하고 멈춘다.

```
입력 파일의 장면과 지금 장면이 다르다.
  파일이 녹화된 환경: OmniReset-Fr3Panda-RelCartesianOSC-State-Play-v0
  파일에 기록된 물체: ['insertive_object', 'receptive_object', 'table']
  지금 장면의 물체:   ['desk_surface', 'peg']
다른 환경에서 녹화된 파일은 재생하기 전에 우리 장면 형식으로 옮겨야 한다.
```

옮기는 코드는 이미 있다. 저장소의 `contract/rl_to_lab.py`가 관절 각도를 우리 장면에서
재생해 손끝 궤적을 뽑고, 물체가 우리 책상 높이에 놓이도록 높이를 옮기고, 초당 20스텝으로
다시 뽑아 우리 형식으로 쓴다. 이 코드가 아직 컨테이너 안에 들어와 있지 않다.

**큐브 시연을 원본에서 다시 만들어 대조하지 못했다.** 지금 쓰는 `fwd_annotated.hdf5` 13편은
예전에 다른 기계에서 만든 것이고, 그 기계의 원본 파일이 이 서버에 없다. 서버 전체를
찾아봤지만 나오지 않는다. 그래서 `make prepare`를 큐브 원본에 돌려 같은 13편이 나오는지
확인할 수 없다. 원본 파일을 확보하면 바로 확인할 수 있다.

**핀 시연도 마찬가지다.** 지금 쓰는 `peg_annotated.hdf5` 4편은 이미 표시가 붙어 있던
파일이다. 서버에 있는 다른 핀 녹화 파일 `peg_source.hdf5` 12편으로는 표시를 붙일 수 없다.
그 파일의 명령이 그 파일 자신의 궤적을 만들어 낸 명령이 아니기 때문이다. 명령이 정확히 0인
235스텝 동안 손끝이 0.51 m 움직인다.

### 데이터의 한계

**핀 꽂기의 시연이 4편뿐이다.** 큐브는 13편이고 그중 12편을 쓴다. 시연이 적으면 만들어진
데이터가 원본 4편의 변형에 머문다. 표시가 붙은 시연을 더 확보하는 것이 다양성을 올리는 가장
직접적인 방법이다.

**핀 꽂기는 명령 잡음을 넣을 수 없어 궤적 다양성이 큐브보다 낮다.** 7장에 적었듯이 잡음을
0.01만 넣어도 성공이 0이 된다. 그래서 에피소드마다 달라지는 것은 핀의 시작 위치와 물리값과
조명과 색과 카메라뿐이고, 같은 배치에서 손이 지나가는 길은 사실상 같다. SART 증강이 이
문제를 접근 구간에서만 부분적으로 푼다.

**핀과 구멍 사이 틈을 물리에 반영하지 못한다.** 물리값 묶음에 그 틈이 0.66 mm에서 1.16 mm
사이라고 적혀 있지만, 그 값은 재질이 아니라 모양이다. 지금 물리 항은 무게와 관성과
무게중심과 재질만 바꾸고 물체 크기는 건드리지 않는다.

**시각 조건 규격의 커튼 두 개를 넣지 못한다.** 규격에 색과 재질은 있으나 3D 모델이 없다.
매 에피소드 건너뛴 항목으로 기록에 남는다.

## 9. 문제가 생겼을 때

아래는 전부 실제로 겪은 실패다. 증상과 원인을 짝지어 적었다.

**단계가 아무 말 없이 끝나고 그다음 단계가 이상한 오류를 낸다.** 시뮬레이터 위에서 도는
스크립트는 파이썬이 예외로 죽어도 종료 코드가 0으로 나오는 경우가 있다. 시뮬레이터를 닫는
코드가 프로세스를 먼저 끝내서 오류 메시지가 화면에 나오기 전에 사라지기 때문이다. 그러면
위 단계는 성공으로 읽고 잘려 나간 파일을 다음 단계로 넘긴다. 지금은 각 단계가 종료 코드
대신 산출물을 직접 열어 판정하고, 오류 메시지를 시뮬레이터를 닫기 전에 찍는다. 그래도
이런 증상이 보이면 로그에서 마지막 예외를 찾는다.

**기록 단계가 모든 에피소드를 버린다.** 로그에 `render replay wrote no success verdict`가
편마다 찍힌다. 렌더 단계가 성공 표시를 남기지 않았다는 뜻이고, 원인은 설정 파일의
`render.success`가 그 작업의 판정 함수를 가리키지 않는 것이다. 실제로 핀 꽂기에서 생성과
변환과 렌더를 다 통과한 10편이 여기서 0편이 된 적이 있다.

**되돌리기가 물체 이름으로 실패한다.** 로그에 `KeyError: 'desk_surface'` 같은 것이 뜬다.
소스 파일이 지금 장면 정의와 짝이 맞지 않는다는 뜻이다. 장면을 고치면 기록되는 물체 목록도
바뀌는데, 고치기 전에 만든 파일에는 그 물체가 없다. 지금 코드로 생성을 다시 돌린 파일을
써야 한다. 증강 단계와 재생 거르기 단계가 시작할 때 두 목록을 대조하고 어느 물체가 없는지
이름을 찍는다.

**물리 재생은 성공인데 영상이 책상 아랫면으로 가득 찬다.** 관절 각도와 물체 위치는 멀쩡하고
재생 성공 판정도 통과하는데 카메라만 엉뚱한 곳을 본다. 렌더 프로세스가 맡은 첫 편은 정상이고
그다음부터 전부 그렇다면 원인은 하나다. 시연 파일의 맨 바깥에 `format_version`이라는 표시가
있는데, 그것이 없으면 Isaac Lab이 그 파일을 옛 형식으로 판단하고 로봇 받침의 회전값 네 숫자를
순서를 바꿔 읽는다. 받침에 적힌 값 `(0, 0, 1, 0)`은 제 순서로 읽으면 z축 180도 회전인데,
옛 순서로 읽으면 y축 180도 회전이 된다. 카메라 세 대가 모두 받침에 매달려 있으니 그만큼
같이 돌아 책상 밑으로 내려간다. 로봇과 물체는 그대로라 수율로도 성공률로도 잡히지 않는다.

표시가 사라지는 자리는 조각 파일 여러 개를 하나로 묶는 병합 단계다. 생성 프로세스를 둘 이상
띄우거나 SART 증강을 켜면 병합이 일어난다. 하나만 띄우고 증강을 끄면 병합 대신 이름만 바꾸므로
표시가 남고, 그래서 이 결함은 오래 드러나지 않았다. 지금은 병합이 표시를 그대로 옮기고,
재생 거르기와 증강과 렌더가 파일을 열기 전에 표시를 확인해 없으면 그 자리에서 멈춘다.
정말로 Isaac Lab 2.x가 녹화한 옛 파일을 읽어야 하면 `--allow-legacy-quat`로 검사를 끈다.

**실행은 되는데 성공이 하나도 안 나온다.** 물체의 회전을 나타내는 네 숫자의 순서를 반대로
잡으면 이렇게 된다. 이 컨테이너는 XYZW 순서를 쓰고 회전이 없으면 `(0, 0, 0, 1)`이다.
반대로 잡으면 회전이 없는 물체가 180도 돌아간 것으로 읽히고, 생성기가 시연의 물체 자세와
지금 물체 자세의 차이로 궤적 전체를 옮기기 때문에 그 180도가 궤적을 엉뚱한 곳으로 보낸다.
실제로 697번 시도 동안 로봇이 핀을 한 번도 건드리지 못했다.

**허깅페이스 데이터 미리보기 화면이 열리지 않는다.** 저장소가 비공개면 그렇다. 그 화면은
로그인 없이 데이터를 가져가기 때문에 비공개 저장소를 읽지 못한다. `.env`의 `HF_PRIVATE=0`으로
두면 공개로 만들어진다.

**저장소에 청크만 있고 데이터셋이 없다.** `make aggregate`를 빼먹은 것이다. 청크는 만들어질
때마다 `chunks/` 아래에 따로 올라가고, 최상위 `meta/info.json`은 합치기가 만든다. 그 파일이
없으면 학습 코드도 허깅페이스 화면도 데이터셋을 찾지 못한다.

**GPU 네 장으로 돌렸는데 4분의 1만 남았다.** 컨테이너마다 `SHARD_ID`가 달라야 한다. 같으면
네 대가 저장소의 같은 자리에 올려 서로 덮어쓴다. `make run-4gpu`는 자동으로 다르게 넣는다.
직접 띄울 때는 `SHARD_ID`와 `SEED_BASE`와 호스트 작업 디렉터리 셋을 모두 다르게 해야 한다.

**증강 성공률이 100%에 가깝다.** 좋은 신호가 아니라 나쁜 신호일 수 있다. 증강이 무너져서
원본을 그대로 복사하면 원본이 이미 성공한 궤적이니 복사본도 전부 성공한다. 실행 기록의
다양성 대비를 본다. 그 값이 3배 아래로 내려가면 실행 기록에 경고가 적힌다.
